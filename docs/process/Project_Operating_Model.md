# Project Operating Model

## 1. Development Cadence

1. Работа идет короткими слайсами (`*.S*`), длительность обычно 0.5-2 дня.
2. Каждый слайс заканчивается рабочим инкрементом, а не только кодовой заготовкой.
3. WIP-limit: максимум 1 активный слайс на разработчика.
4. Формат слайса: вертикальный (`Backend + Frontend + Demo + QA`).
5. Развитие идет вширь по capability-направлениям, а не длинной последовательностью только backend-задач.

## 2. Mandatory Artifacts Per Slice

Для каждого слайса обязательно:

1. Код/тесты/скрипты (если слайс технический).
2. Обновление `Roadmap.md` со статусом.
3. Обновление `README.md` с текущим состоянием.
4. Обновление `System_Architecture_Overview.md`, если менялась архитектура.
5. ADR/ARD при архитектурном решении.
6. Отдельный git commit.
7. Тест-гейт перед commit по типу слайса (`Fast` / `Targeted` / `Full`).
8. Синхронное обновление демо-трека (`docs/demo/Demo_Track.md`) для затронутого функционала.
9. Для фронтовых изменений: explicit подтверждение соответствия `design_system`.
10. Обновление wiki (`docs/wiki/*`) как обязательный артефакт слайса (user + developer + release note).

## 3. ADR Discipline

1. Нет архитектурного изменения без ADR.
2. Один ADR = одно решение.
3. Спорные или измененные решения оформляются новым ADR (supersedes), старые не переписываются.

## 4. Agile Expansion Model (Concentric MVPs)

Развиваем не длинной линейной стройкой, а концентрическими кругами:

1. MVP-1: сквозной минимальный цикл.
2. MVP-2: расширение глубины оптимизации.
3. MVP-3: эксплуатационная зрелость и командный scale.

Критерий входа в следующий круг:

1. Текущий MVP имеет рабочий end-to-end путь.
2. Есть evidence, что следующий круг решает главный оставшийся риск.

## 5. Definition of Ready For a Slice

Перед стартом слайса:

1. Понятна цель и измеримый результат.
2. Определены затрагиваемые модули.
3. Понятны критерии приемки.
4. Ясно, нужен ли ADR.

## 6. Definition of Done For a Slice

Слайс завершен, если:

1. Реализация работает и проверена.
2. Есть проверяемый frontend surface для нового/измененного backend-функционала.
3. Есть runnable demo-путь для ручной проверки результата.
4. Есть покрытие тестами по затронутому пути (`unit + integration + e2e`).
5. Для фронтовых изменений подтверждено соблюдение `design_system`:
   - токены из `design_system/colors_and_type.css`,
   - паттерны/компоненты из `design_system/ui_kits/*`,
   - бренд-ассеты из `design_system/assets/*`,
   - voice/content правила из `design_system/README.md`.
6. Документы обновлены (минимальный обязательный набор).
7. Статус в roadmap обновлен.
8. Сделан commit с id слайса в сообщении.
9. В истории есть подтверждение успешного test-gate для текущего типа слайса.
10. Для слайсов с пользовательскими изменениями есть обновленная wiki-страница:
   - `docs/wiki/releases/<slice-id>.md`
   - релевантные `docs/wiki/user_guides/*` и/или `docs/wiki/developer/*`.

## 6.1. Test Pyramid Policy

Обязательная структура автотестов:

1. `unit`: проверяют изолированную бизнес-логику и валидаторы.
2. `integration`: проверяют связки компонентов и CLI/API-контуры.
3. `e2e`: проверяют сквозной пользовательский путь.

Правило развития:

1. На каждом слайсе расширять все уровни, которые затронуты изменениями.
2. Не допускается merge/commit слайса без зеленого test-gate, соответствующего уровню изменений.
3. Режимы gate:
   - `Fast gate`: frontend-only (`python -m pytest tests/unit/test_frontend_contracts.py` + `python -m pytest tests/e2e/test_frontend_shell_smoke_script.py`).
   - `Targeted gate`: fast gate + `python -m pytest tests/integration/test_frontend_dev_server.py` + профильные backend integration/e2e тесты затронутого API/path.
   - `Full gate`: полный `python -m pytest` (для крупных слайсов и release-кандидатов).

## 6.2. Demo Sync Policy

Правило синхронного развития демо:

1. На каждом слайсе обновлять демо-сценарий текущего уровня зрелости.
2. Для каждого нового функционального инкремента добавлять или уточнять runnable демо-команду.
3. В демо обязательно фиксировать: вход, действие, наблюдаемый результат.
4. Демо не может отставать от функциональности более чем на 1 слайс.
5. Демонстрируемый frontend в демо также обязан соответствовать `design_system`.

## 6.3. Design System Compliance Policy

`design_system` обязателен для всего UI-контура проекта.

1. Не допускаются локальные визуальные отклонения от токенов/типографики/иконографии.
2. Запрещены стили вне правил системы (emoji в UI copy, AI-glow градиенты, glassmorphism).
3. Любая новая UI-компонента либо копируется/адаптируется из `ui_kits/*`, либо оформляется как расширение дизайн-системы.
4. При конфликте между текущей реализацией и дизайн-системой приоритет у дизайн-системы.

## 7. Commit Convention

Формат:

`<slice-id>: <short outcome>`

Примеры:

- `I1.S1: add DSL v0 schema and validation`
- `I2.S2: add node-level trace sink for renderer`

## 8. Fast Onboarding Contract (10-15 min)

Новый разработчик должен прочитать:

1. `README.md`
2. `Roadmap.md`
3. `System_Architecture_Overview.md`
4. `docs/adr/README.md` + последние 1-3 ADR

После этого он должен уметь:

1. назвать текущий активный слайс;
2. назвать следующий слайс;
3. начать реализацию без дополнительной синхронизации.
