# Project Operating Model

## 1. Development Cadence

1. Работа идет короткими слайсами (`I*.S*`), длительность обычно 0.5-2 дня.
2. Каждый слайс заканчивается рабочим инкрементом, а не только кодовой заготовкой.
3. WIP-limit: максимум 1 активный слайс на разработчика.

## 2. Mandatory Artifacts Per Slice

Для каждого слайса обязательно:

1. Код/тесты/скрипты (если слайс технический).
2. Обновление `Roadmap.md` со статусом.
3. Обновление `README.md` с текущим состоянием.
4. Обновление `System_Architecture_Overview.md`, если менялась архитектура.
5. ADR/ARD при архитектурном решении.
6. Отдельный git commit.
7. Полный прогон автотестов (`unit + integration + e2e`) перед commit.
8. Синхронное обновление демо-трека (`docs/demo/Demo_Track.md`) для затронутого функционала.

## 3. ADR Discipline

1. Нет архитектурного изменения без ADR.
2. Один ADR = одно решение.
3. Спорные или измененные решения оформляются новым ADR (supersedes), старые не переписываются.

## 4. Agile Expansion Model (Concentric MVPs)

Развиваем не длинной линейной стройкой, а концентрическими кругами:

1. MVP-1: сквозной минимальный цикл.
2. MVP-2: расширение глубины оптимизации.
3. MVP-3: эксплуатационная зрелость и командный scale.

Критерий входа в следующий круг:

1. Текущий MVP имеет рабочий end-to-end путь.
2. Есть evidence, что следующий круг решает главный оставшийся риск.

## 5. Definition of Ready For a Slice

Перед стартом слайса:

1. Понятна цель и измеримый результат.
2. Определены затрагиваемые модули.
3. Понятны критерии приемки.
4. Ясно, нужен ли ADR.

## 6. Definition of Done For a Slice

Слайс завершен, если:

1. Реализация работает и проверена.
2. Документы обновлены (минимальный обязательный набор).
3. Статус в roadmap обновлен.
4. Сделан commit с id слайса в сообщении.
5. В истории есть подтверждение успешного полного прогона тестов.

## 6.1. Test Pyramid Policy

Обязательная структура автотестов:

1. `unit`: проверяют изолированную бизнес-логику и валидаторы.
2. `integration`: проверяют связки компонентов и CLI/API-контуры.
3. `e2e`: проверяют сквозной пользовательский путь.

Правило развития:

1. На каждом слайсе расширять все уровни, которые затронуты изменениями.
2. Не допускается merge/commit слайса без зеленого полного прогона `pytest`.

## 6.2. Demo Sync Policy

Правило синхронного развития демо:

1. На каждом слайсе обновлять демо-сценарий текущего уровня зрелости.
2. Для каждого нового функционального инкремента добавлять или уточнять runnable демо-команду.
3. В демо обязательно фиксировать: вход, действие, наблюдаемый результат.
4. Демо не может отставать от функциональности более чем на 1 слайс.

## 7. Commit Convention

Формат:

`<slice-id>: <short outcome>`

Примеры:

- `I1.S1: add DSL v0 schema and validation`
- `I2.S2: add node-level trace sink for renderer`

## 8. Fast Onboarding Contract (10-15 min)

Новый разработчик должен прочитать:

1. `README.md`
2. `Roadmap.md`
3. `System_Architecture_Overview.md`
4. `docs/adr/README.md` + последние 1-3 ADR

После этого он должен уметь:

1. назвать текущий активный слайс;
2. назвать следующий слайс;
3. начать реализацию без дополнительной синхронизации.
